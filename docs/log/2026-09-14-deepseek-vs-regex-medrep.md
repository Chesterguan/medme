# DeepSeek 抽取 vs 正则:MedRepBench 683 份实测(2026-09-14)

把「本地 OCR → 脱敏 → DeepSeek → 逐字校验」整条路放到 MedRepBench 683 份真实
中文化验单上,和现有正则路径同分母比,决定进阶版默认走哪一档。

## 怎么跑的

同一遍 PP-OCRv5 出两份产物:未脱敏文本进 ② 几何重建臂(= 生产今天走的
`recognize_engine_layout`),脱敏后文本/涂黑后图片进 ④ 臂送 DeepSeek。
`deid::assert_clean` 在送云之前挡一道,拦下就跳过、计数,不绕过。回来的 JSON
过 `deid::verify` 逐字子串校验:文本档不过就丢,图片档不过就标待核。

模型:**`deepseek-flash`**(两档共用)。计划里写的 `deepseek-v4-flash` /
`deepseek-v4-flash-vision-exp` 是旧名,`GET /models` 已经不列,官方定价文档说旧
名仍然受理、同一档价钱。模型名现在从 `DEEPSEEK_MODEL_TEXT` /
`DEEPSEEK_MODEL_VISION` 读,默认 `deepseek-flash`,运行头和 `halluc.json` 都记着
本轮用的是哪个 —— 换了模型的数字不许和旧数字混进一张表。

图片档不需要切块:小样本 5 份里只有 1 份 labs 为 0(该份文本档也只有 1 条),
没触发计划里「≥3 份为 0 就按行带纵切」的条件。

**和 `text` 同口径的是 `image(仅校验通过)`。**

### 待核 ≠ 编的

把两列相减就能直接量:全量列比"仅校验通过"多出 **777 行**能对上真值指标的
数据,其中**数值对的 743 行(95.6%)**,错的 34 行(4.4%)—— 而校验通过那批
行的错配率是 3.4%。**同一个量级。**

所以图片档的待核不是"模型编的",是**逐字校验的参照物(本地 OCR 文本)太弱,
没法给图上明明存在的那一行背书**。校验在图片档的角色是挡幻觉,不是判对错;
丢掉待核行会连带丢掉 743 条正确数据,还会让 **205/683 份文档变成一片空白**。

## 结论

- **门过了 —— 但必须说清是按哪条处置规则过的。**
  - 按产品实际会发的样子(图片档待核行照发、界面标「需核对」):
    ④ image 80.2/77.5/77.5、④ text 62.8/59.0/57.5,两档都高于 58.7/49.7/24.3。
  - 按「只认校验通过的行」这条更严的同口径:④ text 62.8/59.0/57.5 **过**;
    ④ image 50.4/48.4/47.8 —— 项目召回和值-名配对**低于门槛,不过**。
- **默认仍然定图片档**,理由是上面那 95.6%:待核行绝大多数是对的,产品里它们
  带着「需核对」标记照常显示(Task 4/11 已把 `needsReview` 打通到摘要),用户
  看到的是"这条待核",不是被悄悄喂了错数据。错配率 3.7% 也是四列里最低的,
  不到现状 ② 的三分之一 —— 值安错指标才是最伤人的那类错。
- **文本档不做默认**:项目召回 62.8% 比今天的 ② 几何重建 65.8% 还低,而且贵
  三倍、慢三倍。留作图片超限/隐私更保守时的退路。
- 值得记的:spec 里那组门槛(58.7 / 49.7 / 24.3)是更早一轮的正则基线,这次
  同批数据上 ② 跑出 65.8 / 58.4 / 47.0 —— PR #213 把生产从裸拼接换成布局重建
  之后,基线自己涨了。门槛该刷新成同批实测的 ② 值,别再拿老数字当及格线。
- 上游天花板没动:5068 条真值里 38.9% 的项目名过不了 `terminology::resolve`,
  10.7% 是定性结果。**换模型解决不了这两块**,词表该补还得补。

## 容错校验(同日追加,Task 9b)

上面那 35.8% 待核量的其实是**本地 OCR 的错字率**,不是幻觉率。既然创始人裁决
「质量优先、全部行显示、没过校验的标待核」,就把校验做扎实:图片档的比对放宽到
"同一个字符串的合理写法差异",文本档**一个字不放宽**(仍是逐字子串)。

规则(`packages/deid/src/verify.rs`,每条在 `tests/verify_tolerant.rs` 里有
通过/不通过各一个用例):

- 全角→半角、去空白、大小写;OCR 混淆并成一类:`0/O`、`1/l/I/|`、`5/S`、`8/B`、
  `. / ,`、`- / — / –`、`× / x`、`↑↔H`、`↓↔L`。
- **数值字段解析成数后必须相等**(`0.60` = `.6` = `+0.6`),**永不按"接近"放行**;
  纯字母串不含数字时不许折成数字(`SOS` ≠ `505`)。原文的数先按空白切词再找数字,
  空白分开的两个数不许拼成一个(`115 150` ≠ `115150`)。
- 名字:折叠后与原文某行/某词的**前缀**编辑距离 ≤1,或 `terminology` 把两边解析
  到**同一个术语**(原文印 `WBC`、模型给「白细胞计数」)。两条护栏:三字及以下
  不模糊;命中的那段自己能解析成**另一个**术语就收回(「红细胞计数」与
  「白细胞计数」正好差一个字,那是邻项不是误读)。

离线重算(683 份的 `{doc}.raw.json` + 同一遍 OCR 文本,`medrep_llm --reverify`,
**没有再调一次 API**):

| | 改之前 | 改之后 |
|---|---|---|
| 待核 · 化验条目 | 35.8% (1555/4348) | **13.5% (585/4348)** |
| ④ image(仅校验通过)项目召回 | 50.4% (1285/2551) | **71.7% (1829/2551)** |
| ④ image(仅校验通过)值-名配对 | 48.4% (1234/2551) | **69.3% (1769/2551)** |
| ④ image(仅校验通过)参考区间归属 | 47.8% (1015/2123) | **69.4% (1474/2123)** |
| ④ image(仅校验通过)错配率 | 3.4% (43/1277) | 3.6% (67/1836) |
| ④ image(仅校验通过)整份为空 | 205/683 | **96/683** |

新放行 970 行、收回 0 行(新规则是旧规则的超集)。这 970 行里能对上真值指标的
559 行,**数值对的 535 行 = 95.7%**,与上面那批待核行的 95.6% 一致 —— 放宽放进来的
是同一种"对的数据"。错配率只从 3.4% 抬到 3.6%。

**「仅校验通过」这一列现在三条指标全部高于今天的 ② 基线(65.8/58.4/47.0)**,
上面结论里"按只认校验通过的行、图片档不过门"那条**已经不成立**了。

剩下 585 条待核,按"哪个字段没过"分(一行可能不止一个字段没过,故相加大于 585):
名字 332、单位 116、数值 101、异常标志 57、参考区间 35。抽 30 条手看:18 条是本地
OCR 把名字那一段跨行切开/整段漏识/错两个字以上,6 条是单位漏识或错字超出混淆表
(`fl`→`f`、`pg`→`rg`、上标 `10¹²` → `101²`),4 条是定性/长文本值被 OCR 拆行,
1 条是模型自己推出来的 ↑ 标志(原文没有),1 条是模型真读错了参考上限
(`0-0.119`,原文 `0~0.149`)—— 最后这条正是校验该挡下的。



1. **「脱敏门拦下 0 份」是结构性的,不是"脱敏很干净"的证据。**
   `assert_clean` 只查 `KnownIdentity` 里那三样(姓名/证件号/手机号),而
   MedRepBench 已去标识、没有真身份可填,评测喂的是占位名 `＿评测占位＿` ——
   它按定义不可能出现在语料里,所以这个门在这份数据上**必然**是 0。它证明的是
   "门在送云之前真的跑了、拦下会跳过",不是"脱敏覆盖率 100%"。真实覆盖率看
   Task 5 的 fixture(18 行 HIPAA)和 Task 2/7 的已知缺口清单。
2. **图片档送出去的那张图,从来没被门查过。**
   图片档 `assert_clean` 查的是脱敏后的**文本**,真正离开设备的是涂黑后的
   **图片**。两者的遮盖范围来自同一批检测框(`deid/src/redact.rs:289-334`),
   所以文本门是图片的**代理检查**,不是对图片本身的检查。
   **这是 Task 15(手机接线)和 Task 16(ADR + 隐私政策)必须明写的开放项**:
   要么在 ADR 里把"文本门代理图片"这条限制说出来,要么给图片补一道真检查
   (把涂黑后的图再 OCR 一遍、对结果跑 `assert_clean` —— spec §8 认这条路)。
   **不许默认它等价。** 对外话术同理:说"页眉页脚整带涂黑",不说"保证不漏"。
3. **② 读的是未脱敏 OCR 文本,④ 读的是脱敏后的文本/涂黑后的图。**
   ④ 是带着脱敏代价比的,和产品里真实发生的一致;② 略占便宜。
