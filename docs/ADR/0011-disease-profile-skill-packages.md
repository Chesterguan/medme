# ADR 0011 · 病程档案:一个病 = 一个签名的静态包,规则在手机上跑

Status: Accepted · Date: 2026-09-18

## Context

MedMe 已有的「看懂」摘要是通用的:化验趋势、时间线、就诊,对每个用户一视同仁。这对一个
已确诊的慢病患者帮助有限——同样一张补体 C3,狼疮患者关心的是「比上次低了吗、够不够计一次
活动度」,通用摘要只能说「低于参考区间」。用户 2026-09-16 拍板:先做免疫介导慢病族
(MS/MG/IBD/NMOSD/SLE),第一个病 SLE,界面名「病程档案」,与通用摘要**分开**(未开启任何
包时「看懂」只有通用摘要)。

要做「按病看」,有三条路:(a) 把每个病的规则写进 App,(b) 把病历送到服务端按病分析,
(c) 把规则做成可下发的数据、在手机上跑。选 (c)——理由见下面的「考虑过的替代方案」。

## Decision

1. **一个病 = 一个签名包。** 服务端 `GET /v1/skills/{id}/{ver}.json`,公开静态 JSON,Ed25519
   签名信封盖在原始字节上,公钥编进 `packages/profile`,验不过拒绝加载。包里只有阈值、出处、
   展示顺序,**不含任何用户数据**;拉包的请求不带账号、不带设备号(spec §8)。清单
   `skills/index.json` 用同一种签名信封,同样签名(Task 27)。
2. **降级攻击被结构性挡住。** 客户端对每个包 id 记住见过的最高版本,拒绝安装更低的版本——
   中间人既注入不了内容,也不能把用户按在一个旧规则上。残余面只剩「把本地缓存整个抹掉再喂
   旧包」,需要设备存储写权限,那时攻击者已经能做得多得多的事;当前不为这一点再加防重放层。
3. **App 里只有一个规则引擎(`packages/profile`,纯函数)+ 一个渲染引擎**(7 种 section 类型)。
   加一个病 = 发一个包,不发版;只有需要新 section 类型或新规则类型时才发版(包声明
   `min_engine`)。设计意图是把「病程档案」做成「看懂」页里独立于通用摘要的一块(入口卡 →
   独立页);渲染引擎(`profile_sections.dart`,7 种 section 全部实现)已就绪,入口这一层
   尚未接入,见 Consequences。
4. **抽取用族级 prompt**(schema 2):`facts[]` 的类型枚举对整个免疫介导慢病族是同一份,
   服务端从请求看不出用户是哪个病,请求里永远不带病种/包 id(spec §8)。schema 2 和 schema 1
   走同一条云抽取通道、同一道脱敏硬闸、同一个计量(ADR 0010),按请求的 `schema` 字段二选一,
   各自是一次独立调用(`extract.py:84-94`)。绑住两者不跑偏的是 **prompt** 本身:
   `extract_v2_system.txt` 是去掉结尾 `}` 的 `extract_v1_system.txt` 原文 + 追加的
   `,"facts":[...`,测试 `test_extract_v2_prompt_is_v1_verbatim_plus_facts`
   (`services/api/test_api.py:749`)钉住这一点。两边结果共用同一个反序列化结构体
   `Extraction`,`facts` 字段 `#[serde(default)]`——schema 1 的 JSON 没有 `facts` 键也照样
   解析、`facts` 为空(`packages/deid/src/verify.rs:101-119,1045`)。
5. **零新 `Event` 变体。** 用户主动动作(开启/复发/自评/停药…)走
   `DocumentAdded{doc_type=profile_event}`,与 `self_measurement`/`note` 同一先例
   (ADR 0003 的 CAS + 事件溯源不动),同样以密文形式随保险箱同步、按 vault 追加顺序生效
   ——两条事件落在同一时刻时,取事件列表里靠后的那条为准(vault 追加顺序即同日内的时间顺序)。
   `profile_event`/`note` 都不进通用摘要的临床聚合,只喂 `packages/profile`。`ExtractionAdded`
   只把 `schema` 从 1 升到 2,同事件、同表、同同步清单。
6. **术语覆盖层只能加,不能改。** 包的 `terms` 可以给已有 key 加别名、可以定义全新分析物;
   一旦与内置词典撞 key,内置永远赢(spec §2;`packages/terminology` 里 `max_by_key` built-in
   优先)。这是「加病不发版」的前提,也带来了下面 Consequences 里记的那几个真实缺口。
7. **引擎从不下结论。** 界面不出现「计算 SLEDAI」「判断缓解」字样。每条达标项求值到三种显式
   状态之一——`Hit`/`Missed`/`Unknown`——未评分不会悄悄退化成「不计」,空数据一律 `Unknown`
   而不是 0。化验能算的活动度分永远带「化验可算部分」标签(如 `x/18`),不作为总分展示。
   **每个数值都要能追到一手文献**:出处逐字登记在 `sle-clinical-sources.md`,按
   VERBATIM/PARAPHRASE/NOT VERIFIED 打信度;包里只许引用 VERBATIM 行,其余一律 `null` +
   待核标记,不填近似值(研究阶段抓到过两次工具编造——羟氯喹剂量、ANA 荧光型——已剔除,
   spec §11)。证据本身存**原文印刷的值/单位**,单位换算后的值另存 `*_canonical` 字段,
   界面显示原文、引擎按统一单位判定,两者不混在一起。
8. **提醒只认两类来源,严禁按单项指标发明间隔。** (1) 病级节律——活动期/稳定期的复诊频率
   (指南),复诊时该查哪组指标由包的 `markers` 列出;(2) 药物说明书或指南明示的监测频率。
   两类都给不出数字时(如 MTX/CTX 血常规,说明书只写「定期」),包可以给一个保守默认值,但
   必须显式标「包默认」而非指南/说明书,三者在界面互斥可辨,不许伪装成有出处。

## 考虑过的替代方案

- **服务端按病分析**:被否——要按病算,服务端必须知道用户开了哪个包,这直接违反 schema 2
  已经立下的「请求永远不带病种/包 id」隐私线(spec §8),等于把 ADR 0010 刚建立的边界原地
  推翻。
- **写死进 App**:被否——每加一个病、每改一个阈值、每跟一次指南更新都要过应用商店审核;
  「一个病一个包」的意义就是让这些事不需要发版。
- **纯 prompt 包**(不下发结构化 JSON,而是让端上/云端 LLM 在渲染时按提示词现场推理):被
  否——这会把已经被整套核查流程堵掉的漏洞重新打开:LLM 被问「这个人算不算缓解」,给不出
  拒答就会给一个听起来自信的答案。规则(6)(7)要求的「每个数追到一手文献」「未核实一律
  null」「从不下结论」只有在规则是可 golden 测试的纯函数、且规则本身就是被核查对象时才成立
  ——prompt 不是可核查的东西。

## Consequences

**包作者能做的**:加阈值、加 marker/analyte、加不撞内置 key 的别名、定视图 section 排布、
定监测频率(但必须能标成「指南」或「说明书」出处)——改完重新签名即可发布,不用等应用商店。

**包作者不能做的**:不能覆盖内置术语 key;不能在没有指南/说明书撑腰时发明复查间隔(没有就
必须标「包默认」);不能省略任何数值的 `source` id;不能让界面出现结论性措辞;未签名或签名
对不上内置公钥的包,App 直接拒绝加载,没有例外。

**入口尚未接入。** 规则引擎与渲染引擎(`profile_sections.dart`,7 种 section)在 HEAD 已经
完整,但「入口卡 → 独立页」这一层(`disease_profile_screen.dart`/`disease_profile_card.dart`)
还没有实现——Task 22 只有 brief、没有 report,整个 worktree 没有任何屏幕引用
`profile_sections.dart`。spec §12 原本把这条 ADR 排在 C6、在「C5 渲染引擎 + 看懂页 + 交接单」
之后,这次是 C6 先落地。

**发布前必须有人看,不能只靠脚本**:C4 独立临床核查(Task 19,与写包者不同上下文的 agent,
CLAUDE.md 硬规矩第 3 条「不许自审」)逐条核了 91 个带标量对象(56 个含数值)、22 份一手页面,
90 个 MATCH、1 个无法核实(羟氯喹中文说明书 `label_rule`,程序化抓取被反爬拦下 412,改
`null`)。仍需要人而非脚本收尾的至少三类:
- **羟氯喹中文说明书数值**——需要人拿实物药盒(0.1 g/0.2 g 两种规格)或在能过 NMPA 反爬的
  环境里打开说明书数据库,逐字抄录并把规格、批准文号一起记进 `cite`;
- **GIOP 骨密度复查间隔**——一手来源给的是「every 1–2 years」一个范围,取哪一端是临床判断,
  不是转录,需要人拍板;
- **MTX/CTX 监测间隔**——常被引用的 ACR(American College of Rheumatology,美国风湿病学会)
  2–4/8–12/12 周那套两轮独立核查都没追到一手页,只能停在「包默认」,等有人找到一手来源再
  升级成「指南」。

**这条线顺手挖出的词典/parser 缺口**(不是假设的风险,是构建这个包的过程中真实撞见的 bug,
主仓 `WORKLIST.md` A32 集中记录):
- **UPCR ≠ UACR**(尿蛋白/肌酐比 vs 尿白蛋白/肌酐比):内置词典此前只有后者(`urine_acr`),
  前者的别名被误配到 `urine_acr` 上——蛋白与白蛋白是两种不同的检测。因为覆盖层抢不了已被
  内置占用的 key,这个洞**只能在内置词典里补**(新增 `urine_pcr`,LOINC 2890-2,对照 OMOP
  库核过),不是包侧能绕过去的——顺带也修好了通用摘要里的同一个错。
- **CH50 与 CA50 撞车**(总补体溶血活性 vs 糖类抗原 50 肿瘤标志物):CH50 此前根本不在内置
  词典里,模糊匹配以 1 字编辑距离的预算把它猜成了 CA50——恰好是低补体这 2 分要用的那项检测。
  同样因为覆盖层抢不了内置 key,修法是把 CH50 补成内置条目(LOINC 4532-8)。这类「缩写差一
  个字母就是完全不同概念」的撞车不该吃模糊匹配的编辑距离预算,是通用词典层面的教训。
- **`/HP` 与 `/uL` 撞车,仍未修**:内置 `urine_rbc_count` 只认 `/uL` 与 `10*6/L` 两种单位,
  却带着裸别名「尿红细胞」;报告印「尿红细胞 8 个/HP」时内置优先吃掉这行,包里带 SLEDAI
  血尿阈值的 `urine_rbc_hpf` 拿不到值——血尿那 4 分会静默算不出来,界面不报错、人也看不出来。
  根治要把内置按印刷单位拆成按面积/按体积两个 LOINC key(13945-1 / 5808-1),不是包侧加别名
  能解决的;已入 WORKLIST,尚未修。
- **处方笺「规格 + 用法」两列,规格压过用法,仍未修**:常见真实写法「醋酸泼尼松片 5mg×60片
  用法:7.5mg 每日一次」,`extract_meds` 取的是包装规格 5mg 而不是医嘱用法 7.5mg,
  `latest_dose` 直接读错(`task-16-report.md:170`)。这条比上面几条更直接命中这份 ADR
  自己的规则——错的正是 DORIS `<5mg` 与 `gc_ca_vitd` 的 `≥7.5mg`/`≥2.5mg` 阈值共同读取的
  那个每日激素等效量。语料库已改写绕开这种写法以免把错数钉进 golden,真实处方笺仍会撞上;
  根治在 `packages/parser::extract_meds`,还没做(`WORKLIST.md` A32 ⑥)。
- **给药途径写在剂量之后,仍未修**:如「甲泼尼龙片 40mg 每日一次 静滴」,parser 的
  `strip_trailing_route` 会把尾部途径剥掉,规则引擎的剂型门看不到,会把一次静脉冲击按口服
  等效量换算。已用一条测试钉住今天的真实(错误)行为——修好那天它会变红——根治需要
  `MedObservation` 把 `route` 一路带到 `MedSpan`,还没做。

**C1 类教训:门控要看「最新那一条」,不能看「历史并集」。** 剂型门最初读
`MedSpan.raw_names`(一个药所有历史提及的并集),病历里出现过一次静脉冲击后,之后每次口服
都被永久拒绝换算——这条路径被「换算表还是 `null`」意外挡了好几个任务,直到 Task 19 把
`pred_equiv` 填成真数字才第一次真正触发;改读 `latest_raw_name`(与 `latest_dose` 同一条
提及记录的原始写法)修好。**教训可复用**:「取最新状态」的判定若实现上用的是历史集合而不是
最新一条记录,正确性会被上游某个偶然条件挡着,直到条件消失才现形——审这类门控要问一句
「它看的是并集还是最新一条」。具体经过见核查记录(下方链接)§九。

## 与既有 ADR 的关系

- 不影响 [0003](0003-content-addressable-storage.md)(CAS + 事件溯源):零新事件类型,
  `profile_event` 走既有 `DocumentAdded` 路径。
- 不影响 [0005](0005-ocr-per-platform-native.md)/[0006](0006-ios-ocr-pp-ocrv5.md)/
  [0007](0007-android-doc-scan-degms-and-geometry.md)(OCR 分平台):抽取的输入不变。
- 建立在 [0010](0010-cloud-llm-extraction-and-accounts.md) 之上:schema 2 与 schema 1 共用
  同一条云抽取通道、同一道脱敏硬闸、同一个计量,这条 ADR 只加 `facts[]`,不改传输/账号/
  计费模型。
