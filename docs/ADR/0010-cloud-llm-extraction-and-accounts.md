# ADR 0010 · 云 LLM 结构化抽取(本地脱敏后送境内模型)+ 账号

Status: Accepted · Date: 2026-09-14

**Supersedes**:[0005](0005-ocr-per-platform-native.md) / [0006](0006-ios-ocr-pp-ocrv5.md) 隐含的前提
「**识别整条链路都在端上完成**」;以及 memory `ocr-v1-decisions-no-cloud` 里那条
「**第一版不用云 OCR / 不走云**」的原则。

**没被 supersede 的**:0005/0006 的 OCR 路由表一个字都没变——OCR **仍然全部在端上**
(移动端 PP-OCRv5,`ocr_bridge.dart:48`/`:72`;桌面各平台原生)。变的是 OCR **之后**那一步。
分享包 / 代拍链路的 E2E 不变;查看器永不埋点([0009](0009-no-analytics-in-viewer.md))不变。

## Context

正则抽取(`parser::assemble_summary`)在 MedRepBench 683 份真实中文化验单上,同批数据实测
**65.8 / 58.4 / 47.0**(项目召回 / 值-名配对 / 参考区间归属),错配率 **12.5%**——「值安错指标」
是最伤人的一类错。行对齐路线 2026-08-14 实测倒退,已否决
([log](../log/2026-08-14-row-alignment-attempt.md))。

团队 2026-09-11 决定做进阶版(总纲
`docs/superpowers/specs/2026-09-11-advanced-edition-overview-design.md`)。
这要求推翻一条明确写过的原则,所以单开一条 ADR 记账。

## Decision

1. **OCR 留在端上**,它的职责多了一项:**脱敏与定位**。结构化识别交给云端 LLM。
   模型由环境变量决定(`DEEPSEEK_MODEL_TEXT` / `DEEPSEEK_MODEL_VISION`,默认
   `deepseek-flash`,`services/api/extract.py:5-6`)——**不绑定某个模型**,实际跑的那个
   名字由服务端回给客户端、随结果落进保险箱(`extract.py:69-70`)。

2. **生产默认 = 图片档。** 一份文档导入落库后,自动走:
   本地 PP-OCR → `deid::redact_text`(K 已知值 → A 锚点 → P 模式 → 日期偏移,
   `packages/deid/src/redact.rs:36-46`)→ `deid::assert_clean` 硬闸
   (`gate.rs:4-25`,拦下即退回正则)→ 按同一批检测框把**喂给识别引擎的那份画面**涂黑
   (`redact_boxes` 四类矩形含页眉带/页脚带,`redact.rs:331-401`;`ocr::redact_image`
   画黑框后重编码 q85 JPEG,`packages/ocr/src/lib.rs:993-1014`)→ 经**账号会话**
   `POST /v1/extract`(`cloud_extract.dart:106-113`)→ 我们的代理 → DeepSeek。
   **文本档只是退路**(涂黑不可用 / 没有检测框 / 图片超 2 MiB 时),不是默认。

3. **保留与偏移**:年龄、性别、科室、检验值保留(`anchors.rs:64-67` 把这三个词钉成硬停止点);
   日期按**档案**统一偏移 ±90 天(`dates.rs:9-17`,HMAC(档案秘密, "date-shift")),
   LLM 看到假绝对日期、真相对顺序,回来时减回。

4. **结果本机逐字校验**(`deid::verify`)。图片档放宽到「同一字符串的合理写法差异」
   (全角/空白/大小写、OCR 混淆对、数值解析后**相等**而非接近、名字编辑距离 ≤1 或解析到同一术语),
   文本档一个字不放宽。**没过校验的行照常显示、标「需核对」**
   (`lab_status.dart:201-218`),不丢——理由见下。

5. **落盘**:`Event::ExtractionAdded`(`core-model/src/event.rs:61-69`),结果 JSON 进 CAS、
   事件只引 hash,latest-wins,**原件永不动**,换模型可全量重跑(`types.rs:325-345`)。

6. **只走我们的代理与 key**,按订阅计费,不做 BYOK。代理**不落盘 payload**,
   只累加 token 数(`app.py:449-455` → `db.usage_add`)。

7. **对外话术两句分开说**:「存储端到端加密」/「识别时经本地脱敏后送境内云端」。
   **不再说「数据不出手机」。**

## Consequences

### (+) 质量

同一批 683 份、同分母(log:[2026-09-14](../log/2026-09-14-deepseek-vs-regex-medrep.md)):

| | 现状正则(②) | ④ image 全量 | ④ image 仅校验通过 |
|---|---|---|---|
| 项目召回 | 65.8% | **80.2%** | 71.4% |
| 值-名配对 | 58.4% | **77.5%** | 69.1% |
| 参考区间归属 | 47.0% | **77.5%** | 69.2% |
| 错配率 | 12.5% | **3.7%** | 3.6% |

待核 **14.3%**(622/4348 条化验条目)。以上「仅校验通过」列是**容错校验 + 三轮 fix 之后**
的数字([log](../log/2026-09-14-deepseek-vs-regex-medrep.md):141-142);**三条指标在两种口径下都高于现状基线。**

**spec §6 的门槛 58.7 / 49.7 / 24.3 已过期**——那是更早一轮的正则基线;PR #213 把生产
从裸拼接换成布局重建之后,基线自己涨到了 65.8 / 58.4 / 47.0。**以本 ADR 这张表为准**,
spec 不改(spec 是当时的决定,不是活文档)。

**为什么待核行照发而不丢**:两列相减可直接量(按估算,非逐行核出)——全量比「仅校验
通过」多出的 550 行里,数值对的约 **96.0%**(528 行),而校验通过那批的错配率是 3.6%,
同一个量级。**待核不是「模型编的」,是本地 OCR 这个参照物太弱,没法给图上明明存在的
那行背书**。丢掉它们会连带丢约 528 条正确数据,并让 97/683 份文档变成一片空白。

### (−) 代价与已知缺口(必须原样写进隐私政策)

- **脱敏后的病历内容会离开手机**到 DeepSeek。脱敏不可能 100%:手写名、二维码、印章都可能漏网。
- **图片档送出去的那张图,从来没被闸查过。** `assert_clean` 查的是脱敏后的**文本**,
  真正离开设备的是涂黑后的**图片**;两者的遮盖范围来自同一批检测框,所以文本闸是图片的
  **代理检查,不是对图片本身的检查**。补法(把涂黑后的图再 OCR 一遍跑 `assert_clean`)spec §8 认,
  **没做**。对外只说「页眉页脚整带涂黑」,**不说「保证不漏」**。
- **校验的证据是整份文档的 OCR 全文,不是对应那一行。** 值/单位/名字虽已补上锚点与词边界
  (`verify.rs:503-548`),但一个值仍可能被文档别处一个同形的字符串背书。这是这套校验的天花板。
- **名字那 332 条待核是 OCR 问题**,不是校验能解决的(跨行切开、整段漏识、错两个字以上)。
- **文本字段(`MedItem.dose/freq/route`、`impression`、`notes`)只有逐字子串**
  (`verify.rs:534`,`FieldKind::Text`),没有数值那种解析后相等的强规则。
- **有一个开关,跟设备走。**「设置 → 账号 → 云端整理」(`account_screen.dart:1177-1192`),
  默认开(`cloud_extract.dart:34-46`,键 `cloud_extract_enabled`,`account.dart:29`)。
  **每份文档发出去之前都重读一次**(`cloud_extract.dart:161`):一批导入要跑好几分钟,
  用户跑到一半关掉,剩下的几份就不发了,连网络都不碰。
  退出登录也会让这条通道停下来(没登录 = 没这个功能,`cloud_extract.dart:239-245`)——
  但那是因为 `session.access` 没了,不是这个开关本身被清掉:它跟设备走,
  `AccountSession.clear()` 不动它(`account.dart:25-29`),下次登录仍是上次留下的状态。
  成员的「云同步」开关**管不到它**——那条路只看 `session.access` 与这个独立开关
  (`cloud_extract.dart:153-180`)。
- **换机「旧设备扫码批准」的密钥对探针挡不住整对替换**
  (`docs/superpowers/specs/2026-09-11-account-keys-sync-design.md:89-110`):
  服务端自造一对真密钥即可通过探针。堵法是双向指纹确认,**没做**;口令 / 恢复码两条路没有这个缺口。
- 依赖网络;离线、闸拒发、上游失败一律静默退回本地正则,导入本身不受影响。

### 发版顺序(多设备兼容)

**先把新版本铺到该账号的所有设备,再开云端整理。** `ExtractionAdded` 是新事件类型,
老版本的二进制不认识它:本机读到只会跳过这一条(不再连累它后面那条,见
`core-model/src/log.rs` 的 `Event::Unknown` 兜底),而同步拉取路径会把它算作「解不开」
——就地截断那台设备、计一笔 `undecodable`、水位不推进(`vault_sync.rs` 的
`sync_import_events`)。**数据不会坏、也不会丢**(升级之后原样重拉即可),但在升级之前,
老版本设备上**永远看不到任何抽取结果**,而且每次同步都会在那个设备段上停住。
反过来也一样:老设备写的事件新版本全认得,所以顺序只有这一条约束。

### DeepSeek 侧(2026-09-14 核查,见报告引用)

其隐私政策自称适用于 API,并称境内运营收集产生的个人信息**存储于中国境内**;
其中的「输入/输出可能用于模型训练」条款配一个产品内开关,而**开放平台服务协议**本身
既无训练授权条款、**也没写保留期限**。**我们无法核实**具体保留多久、以及那个开关是否
覆盖 API 账号——隐私政策里如实这么写。
